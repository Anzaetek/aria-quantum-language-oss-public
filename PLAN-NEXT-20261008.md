## Phase A — matched f64 rows against cuStateVec (STATUS §5 #17, follow-on to #19)

### What blocks honest rows today

- **The reduction would dominate the row.** `CudaStatevectorF64Backend::expectation`
  reduces on the host, one single-threaded `expectation_pauli` pass per term. E5's
  observable has 2n−1 terms (47/51/55 at 24/26/28q), so at 28q that is ~1.5e10
  serial iterations (~15-30 s), against cuStateVec f64's ~2 s on-device
  reduction. A row would time our host loop rather than the f64 simulator.
- **Fusion is not matched.** Our f64 arm is one launch per gate. cuStateVec has
  only a `fused-f64` variant (an untimed context control). A matched row needs
  `unfused-f64` on their side.
- **The 28q oracle is circular.** Above `ORACLE_MAX_QUBITS` = 26 the reference
  is arm-against-arm, cuStateVec f64 vs Aer-GPU f64. With cuStateVec as the
  competitor, it would be its own referee.
- **Host memory.** `StateF64::zero` builds the full state on the host, and
  `evolve` holds two host copies at once. That is ~8 GiB peak at 28q, against
  the lane's 6G hostgate cap.
- **Harness gaps.** `ours.rs` is hard-wired to the f32 backend. `GATE_REL_F32`
  is hard-coded at four row-stage sites, `state_mib` assumes complex64, and
  `run.sh`'s cap-kill void id would void the f32 row.

### Steps

1. **On-device f64 Pauli reduction.**
   - `KernelsF64` compiles `pauli_expectation` at `Precision::F64`; the kernel is
     already precision-generic.
   - `StateF64::pauli_expectation` gets f64 partials, `block*16` shared memory
     and an f64 `y_factor`.
   - `expectation` uses it.
   - The host `expectation_pauli` path stays only as the test oracle.
   - **Test:** device vs host reduction ≤ 1e-12 on the every-gate circuit and on
     E5's observable at 20q. Odd-Y terms are included, because the Y sign is the
     known trap.
   - **A10:** y_factor conjugated, partials typed f32, sign mask dropped — each red.
2. **Host-memory diet.**
   - Allocate |0…0⟩ on the device (`alloc_zeros` plus one 16-byte write), not
     via a full host vector.
   - `evolve` converts in place, so there is one host copy, and only when a
     statevector is asked for.
   - The `expectation` path never copies the state to the host.
3. **Harness.**
   - `Engine::OursF64`, labelled `omega-cuda-f64`, with `is_f64` true and knobs
     stating "f64 state, unfused, device reduction".
   - `ours.rs` selects the backend from an env var and asserts `name()`.
   - `Variant::UnfusedF64` in `client.rs` and `custatevec_arm.py`.
   - The row stage takes its tolerance from `is_f64` (`GATE_REL_F64` = 1e-10);
     `state_mib` is ×16 for f64.
   - New ids: `gpu-{cell}-o-expectation-f64-vs-custatevec`. `run.sh`'s void id
     follows the variant, and the lane's host cap is raised for f64.
   - **28q:** f64 rows run only where an independent reference exists. That is
     the Aer CPU f64 oracle (≤ 26q), or Aer-GPU with `cuStateVec_enable=False` if
     it runs at 28q on this card. If neither is available, 28q is a stated
     omission, not a row.
4. **Measure on akilles.**
   - Only with the card free (no holders, util ≤ 10%) and the pre-row census
     attached (Phase B makes the GPU lane carry it).
   - In the same commit:
     - rows appended with `--append`;
     - doc table and loss table citing every new id;
     - `doc_rows` floor raised by the number of new rows, and its stale "35"
       comment fixed;
     - the precision fields `ours: f64, competitor: f64, matched: true`.
   - E5's f32 rows are untouched.

**Done when** every new row passes `check`, `doc_rows` is green with the floor
raised, and a reviewer has re-run one row and matched the number.

## Phase B — a per-row external-CPU rule (STATUS §5 #21)

### Evidence on both sides (2026-10-08)

- **MPS lane (CPU, 32 rayon threads):** our arm reproduced within 2-4% from
  depth 12 up across `load_before` 6-26, with external CPU under 8 cores. The
  8.0 threshold was adequate.
- **GPU lane (single host thread driving the card):** a row moved 48% (96 ms →
  142 ms) at 2.5 external cores, with no GPU holder and 1% utilisation. 8.0 is
  far too loose there. (Andromeda's measurement. Its constant
  `EXTERNAL_VOID_ABOVE_GPU_LANE = 1.0` is not on main, and as written it
  contradicts `row_schema.rs:695`, which refuses 1.0. I have asked for the
  data.)
- **Short rows:** sub-millisecond rows sit in a census window padded to 2 s, so
  the census cannot speak for them at any threshold.
- **Three lanes still gate on `load1` with no pre-row census:** dense, gpu and
  pauliprop. §5 #21 says the census is "wired in every lane"; that is false.

### Steps

1. **The rule, in `load.rs`, one place.**
   `external_void_above(lane: Lane, cores: usize) -> f64` returns:
   - **1.0 for `DenseGpu`** (measured);
   - **`load_void_above(cores)` for the CPU lanes** (2.0 / 8.0, measured
     adequate on MPS).

   Short rows: a row whose own minimum is under the census floor
   (`CENSUS_MIN_WINDOW_S` = 2 s) is classified directional-only by `check`
   unless its external figure is ≤ 1.0. This is the "sub-ms rows are not a
   band" rule that §5 #16 already applies by hand.
2. **`writer.rs::check`** gates `external_cores_before` and
   `external_cores_during_row` on `external_void_above(row.lane, …)`. The
   `{2.0, 8.0}` pin becomes "`void_above` equals the lane's rule".
   `row_schema.rs:695` is rewritten to pin the per-lane table on both sides:
   1.0 is refused for a CPU lane and required for the GPU lane.
3. **Wire the pre-row census into dense, gpu and pauliprop**
   (`wait_quiet_external` + `with_pre_row`), replacing their `load1` waits. The
   source scan in `load_threshold.rs` gains these lanes and `cv`.
4. **Migration, stated rather than hidden.**
   - Committed rows without a census keep the `load1` fallback that `check`
     already applies.
   - The six GPU rows are re-measured in Phase A's run with the pre-row census.
     They then pass the 1.0 rule or become void with the reason.
   - Dense/pauliprop rows are not re-measured here; the doc says which rows were
     gated by `load1` only.
5. **A10:**
   - GPU row at external 2.5 → red;
   - CPU row at 6 on 32 cores → green;
   - a sub-floor row at 3 cores → directional;
   - the lane table collapsed to one value → red.

**Done when** `every_published_row_passes_every_check` is green with the new
rule. Every row that changes classification is listed in the commit.

Coordination: andromeda has related local work (the GPU constant, and a census
test redesign). Nothing of theirs gets overwritten. Their GPU figure enters
with their numbers cited, or not at all.

## Phase C — the example angle audit (STATUS §5 #14)

### Corrections to STATUS that the research forces

- There are **44** `.aria` examples, not 48 (aria-verify's registry has 50
  entries, some not `.aria`).
- They are not all structurally blind:
  - **24** already check against an independent or closed-form reference;
  - **6** check task-level or self-consistency only;
  - **11** are same-IR forward-⟨Z⟩ only, and truly blind;
  - **4** are not run by aria-verify (qec_grover/qft/qpe go through aria-qec;
    shor_ecdlp does not lower).
- `qsvt_invert` claims `@prove "qsvt_inversion_polynomial"` but ships `RZ(0)`
  placeholder phases. As written it is not QSVT.
- `examples/aria/README.md` says bell/qpe/simon/superdense have no harness. They
  do.

### Steps

1. **Make "would a wrong angle be caught?" a measurement, not a claim.**
   - An env override for the examples directory, used only by tests.
   - A mutation sweep: for each aria-verify app that loads a `.aria`, perturb
     each rotation-angle expression in a temp copy (θ → θ + 0.1, and a sign
     flip) and run the app's own check.
   - The output is a committed matrix, app × angle site → caught or missed.
   - A test re-runs a fast subset, so the matrix cannot go stale silently. The
     full sweep is a tool, because it is minutes long.
2. **Give the blind ones a referee where one exists.**
   - `qasm_gpu` (a Bell state): closed form.
   - `iqp_born`: closed-form ⟨Z⟩.
   - `quantum_kernel`: kernel = |⟨ψ(x)|ψ(x′)⟩|², computed from the feature map's
     formula, not from the IR.
   - Each test is mutation-proven with an angle perturbation that the old
     forward check passed.
   - The parametric ones (qcnn, qcbm, qgan, qclassifier_rich, qssl, sketch_qml,
     strongly_entangling) have no specification beyond the circuit itself. They
     are recorded as un-refereeable in STATUS, by name, rather than given a fake
     oracle.
3. **qsvt_invert.** Either compute real QSVT phases for the inversion
   polynomial and check A⁻¹b against a closed form, or withdraw the `@prove`
   claim and say why. Decide after reading `qsvt.rs` and the proof file. The
   default is to withdraw the claim, unless the phases are already available in
   the tree.
4. **STATUS §5 #14 and the README** corrected in place with the counts above
   and the sweep's result.

**Done when** the sweep matrix is committed with its test, the three
refereeable blind examples have independent checks, and every missed
mutation is either fixed by a check or listed as un-refereeable with the
reason.
