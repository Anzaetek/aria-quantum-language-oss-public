### B1 — `u` is the last import gap *(small, unblocks two files and §3)*

Both failing files need `u(θ,φ,λ)`: one uses it directly, the other inside
`gate unitary_… { u(…) … }` bodies produced by an external exporter's
unitary-synthesis path.

`u` and `u3` are the **same operator** — verified against the reference
implementation, `max|Δ| = 0.000e+00`. So this is a spelling entry, not a new
gate, and it sits beside the existing `"u3" | "U"` arm.

`p` is already accepted (`"u1" | "p"`), so that half of the report is stale.

**Also worth reporting back:** the round-trip asymmetry §1 describes has been
removed *at its source* since the report was written. The exporter no longer
writes `cp`, `rxx`, `rzz` or a bare `ryy`; it writes qelib1 spellings and
preamble `gate` definitions, so 24 of 25 gates now load in the reference
implementation's **strict** parser. The importer keeps accepting the old
spellings — reading widely and writing narrowly.

### B2 — **The 128-qubit "MPS wrong counts" is a `u64` counts key, and it affects every backend**

This is the priority item, and the diagnosis in the report is wrong in a way
that matters: fixing MPS would not fix it.

**Reproduced exactly.** The 128-qubit GHZ returns `|0^64 1^64>` where `|1^128>`
belongs. But the boundary is not "between 64 and 128" — it is *exactly* 64:

```
  GHZ  63:  |0…0>, |1…1>            correct
  GHZ  64:  |0…0>, |1…1>            correct
  GHZ  65:  |0…0>, |0 1^64>         one leading zero
  GHZ  66:  |0…0>, |00 1^64>        two leading zeros
```

One lost bit per qubit above 64. That is not a truncation threshold and not a
qubit-ordering pathology; it is a 64-bit container.

**Confirmed in the code:** `ExecResult::Counts(HashMap<u64, u32>)`. The outcome
key is a `u64`, with no guard anywhere on qubit count.

**Confirmed not to be MPS.** The same GHZ at 65 qubits on the **stabilizer**
backend truncates identically. Any backend returning counts above 64 qubits is
affected; MPS is simply the one that can reach 128 qubits easily, which is why
it was found there.

The physics is fine. The *reporting* silently drops the high bits — a confident
wrong answer, which is the worst failure mode this repository has, and the same
class as every defect fixed in the export work this week.

**Fix, in order of what must be true first:**

1. **Refuse before returning.** Any execution that would key counts by more than
   64 qubits must fail with a message naming the limit — today, not after a
   representation change. A wrong answer must stop being returned before it
   stops being possible. This is the whole of the user-visible fix and it is
   small.
2. **Then decide the representation.** Options, to be chosen with measurement
   rather than taste:
   * a bitset key (`SmallVec<[u64; N]>` or `Vec<u64>`) — exact, invasive, and
     it touches every backend and the wire format;
   * a string key — simple, allocation-heavy in the sampling loop;
   * keep `u64` and cap at 64 qubits permanently, documented — honest, and
     defensible if nothing needs >64-qubit counts, but it forecloses the MPS
     and stabilizer backends' main advantage, which is exactly the regime
     above 64 qubits.

   The third is not obviously wrong: counts over 128 qubits are a sparse
   sample of a 2^128 space, and a caller usually wants marginals or an
   expectation instead. Whichever is chosen, state the reason.
3. **Tests must span the boundary.** 63, 64, 65 and 66 qubits, on at least two
   backends. A test at 64 and 128 only — which is what the report exercised —
   cannot distinguish "u64 key" from "ordering bug", and that ambiguity is what
   produced the wrong diagnosis.

**What could make this pass for the wrong reason:** asserting on the *number* of
distinct outcomes. GHZ yields two either way — the truncated result also has
exactly two keys. The assertion has to be on the key *contents*, all-zeros and
all-ones.

### B3 — Statevector single-threaded per circuit *(performance)*

The report measures 6.7× at 24 qubits and a timeout at 28 against a reference
simulator, and attributes it to parallelism being applied only across parameter
rows, not across amplitudes within one gate application.

Not re-measured yet; that is step one, because a performance claim without a
local baseline is not actionable and the machines differ.

**Sequence:**
1. Reproduce locally and record the numbers, including the shape of the gap as
   qubit count grows — a constant factor and a growing factor point at
   different causes.
2. Parallelise the amplitude loop by stride. This is contained and does not
   change results.
3. Only then consider gate fusion, which *does* change the order of floating
   point operations and therefore the last bits of every result. If it lands,
   the differential cross-checks are the gate on it, and any tolerance change
   must be justified rather than widened until green.
4. Regardless of outcome, the documented guidance should say what the CPU
   statevector backend is good for, rather than leaving a user to discover the
   cliff at 28 qubits.

### B4 — MPS anomaly on one 19-qubit chain *(blocked)*

~2000× slower than the reference on one low-entanglement chain, while faster on
a comparable circuit. **Cannot be reproduced until B1 lands** — that file needs
`u` to parse.

The report suggests this shares a root cause with the 128-qubit counts problem.
B2 shows that one is a `u64` key with no bearing on runtime, so **that link is
broken** and this needs its own investigation: bond growth, qubit ordering, or a
truncation threshold that never triggers on this shape.
