# Plan — what is actually open, as of 2026-08-25

Written after the `-public` merge (`5b2c23d`) landed 458 files and 9 crates into
this tree. **Every row below was re-checked against the merged code**, not
copied from `STATUS.md` §5 — because three of those entries turned out to be
stale, and a stale open-item list is worse than no list: it sends the next
person (or agent) to re-solve something that is already closed, and it makes the
entries that ARE live look equally doubtful.

## 0. Method, and why it is stated

Each row names **how it was verified**, so a reader can re-run the check instead
of trusting this file. Rows whose evidence is "a doc said so" are marked as
such and are the ones to distrust first.

Two rules this plan is held to, both learned the hard way in the session that
produced it:

* **A test must be shown to FAIL without its fix.** Three separate defects here
  were found only by fault injection; in two of them the test that was supposed
  to catch the bug passed against the broken code. Reading the code did not find
  any of them.
* **Exact claims get exact assertions.** Where a rewrite is bit-identical, the
  test asserts `to_bits()` equality, not a tolerance. A tolerance would pass on
  a fast path that had quietly changed floating-point association, which is
  precisely what such a test exists to catch.

## 2. Live and actionable on this machine

### 2.1 CPU statevector runs sparse 2q gates as dense 4x4 — `PLAN-SV-PERF` S1b

**Verified live**: `CY`, `CZ`, `Swap` and `CRz` all routed to the generic
`apply_2q` (`sim.rs:700,707,714,721`), which costs 16 complex multiplies and 12
adds per group. `CZ`/`CRz` are diagonal; `Swap` is a permutation; `CY` is
anti-diagonal. Only `CX` had a fast path.

* **[DONE]** Diagonal 2q fast path — 4 multiplies per group, no adds.
  Detected **from the matrix** (`diagonal_2q`) rather than routed per call site,
  so `CZ`, `CRz`, `CU1`/`CPhase` and any diagonal gate added later take it with
  no dispatch table to keep in sync. Checked AFTER the q0/q1 relabel, since
  `q0 < q1` swaps diagonal entries 1 and 2. Bit-identity pinned against the
  retired dense scan kept verbatim in `group_walk_equivalence`; both the
  unrelabelled-matrix bug and a d[1]/d[2] slot swap were fault-injected and
  caught.
* **[DONE]** `Swap` as a permutation — only the |01>/|10> pair is read.
  **This bullet said "bit-identical by construction" until 2026-08-27**, which
  is the exemption retracted in `4c97550`. The kernels, comments and tests were
  all corrected and THIS DOCUMENT WAS NOT — found by a reader who happened to
  know the sentence was wrong, which is not a mechanism. The repeatable version:
  a retraction needs a grep for the RETRACTED WORDS across every surface, not
  just the one being edited.
  Detected from the matrix (`is_swap_2q`) on the same reasoning as the
  diagonal. Exact equality in the detector is load-bearing: iSWAP differs from
  SWAP only by phases on those two entries, and a norm-based comparison would
  accept it and silently drop the `i` — fault-injected and caught.
* **[DONE]** `CY` off the dense path — generalised to **controlled-U**, which
  also covers `CU3` and any `CH`/`CU1` added later. Detected on the
  UNRELABELLED matrix (`controlled_1q`) and applied with a mask/scatter kernel
  like `apply_cx`, so the q0/q1 relabel never arises. Skips the control-zero
  half entirely — half the state is not even read.

  **This one is NOT bit-identical, and the reason is worth keeping.** Two
  separate signed-zero effects, found by testing rather than by reasoning:

  1. On the ACTED-ON half it *is* bit-identical, but only because the kernel
     carries a leading `ZERO_C +`. The dense path computes
     `((0*a00 + 0*a01) + m0*a10) + m1*a11`; without that add, a product landing
     on `-0.0` comes out `-0.0` here and `+0.0` there. The add looks like dead
     weight and is not — a comment says so, and removing it fails the test.
  2. On the CONTROL-ZERO half they differ and **cannot be reconciled without
     giving up the optimisation**. The dense path WRITES that half
     (`1*a00 + 0 + 0 + 0`) and the write normalises `-0.0` to `+0.0`. Not
     reading it is the entire point, so a `-0.0` there now survives where it
     used to be silently flipped.

  Unobservable in every way this project measures (`-0.0 == +0.0`, same |z|^2,
  same sampling), but recorded because a bit-equality harness comparing this
  backend against its own history would see it. The test asserts numeric
  equality everywhere, bit-identity on the acted-on half, and that any
  control-zero difference is *exactly* a signed zero — anything else fails.
* **[DONE]** Measured, n=22, M5 Max, best-of-5, per-gate warmup AND
  interleaved gate order, both outside the timed region
  (`examples/sparse2q_bench.rs`; A/B by disabling detection):

  | gate | dense 4x4 | fast path | speedup |
  |---|---|---|---|
  | `cz` | 1.472 ms | 1.111 ms | 1.33x |
  | `crz` | 1.466 ms | 1.166 ms | 1.26x |
  | `swap` | 1.465 ms | 1.152 ms | 1.27x |
  | `cy` | 1.532 ms | 0.949 ms | **1.61x** |
  | `cu3` | 1.507 ms | 0.924 ms | **1.63x** |

  The baseline spread is 4.5% across five gates that share one dense kernel,
  which is the sanity check that this measures the kernel and not the harness:
  with the fast paths off they SHOULD be indistinguishable. Treat the numbers
  as ratios, not constants — run-to-run variance is around 10%.

  `cy`/`cu3` win most because they skip half the state rather than doing less
  arithmetic on all of it. That is the same fact as the modest diagonal
  numbers seen from the other side: **this kernel is memory-bandwidth bound at
  this width**, so what pays is not touching memory, not saving flops. Quoting
  a flop ratio for any of these would overstate them — the diagonal cuts 16
  multiplies and 12 adds to 4 multiplies and buys 1.3x, not 4x.

  **The first version of this bench reported a 2.5x REGRESSION** for what is a
  speedup. It timed `cz` first, so `cz` absorbed the first-touch page-fault
  cost of a 64 MB allocation, and the gates then showed a monotone warming
  curve that reads exactly like a real ordering effect. The numbers were
  plausible and internally consistent; only their SHAPE gave it away. Two
  defences now, and the second is the general one:

  * warm up outside the timed region, and
  * **interleave the gate order across rounds** — the contamination is
    POSITIONAL, not per-gate, so a fixed order lets it settle on whichever arm
    leads and masquerade as signal. Rotating spreads it into noise across every
    arm. Worth doing in any future bench in this repo.

* **[DONE]** `Rbs` via a {|01>, |10>} subspace kernel (`middle_block_2q`),
  which also covers any XY/iSWAP-family gate of that shape. |00> and |11> are
  fixed points and are not read. SWAP has the same FORM and is deliberately
  caught by the cheaper permutation dispatch first — asserted, so reordering
  the chain fails rather than silently slowing down.

* **[CORRECTION, and the important entry on this page]** The bit-identity
  claim made for the diagonal and controlled-U paths was **FALSE**, and both
  shipped with it (`98403d4`, `0ef773d`).

  No dispatch that skips reading amplitudes can be bit-identical to the dense
  4x4. The dense row is `g0*a00 + g1*a01 + g2*a10 + g3*a11` with some
  coefficients exactly zero, and `0.0 * a` is `-0.0` when `a` is negative — so
  the dense RESULT carries sign information from amplitudes the fast path never
  reads. Measured by enumerating sign combinations: the diagonal differs in
  **7 of 16**, controlled-U in 3 of 16.

  Adding a leading `+ 0.0` cut controlled-U's 3 to 1 and I mistook that for a
  fix, wrote "load-bearing" in a comment, and shipped it. It cannot be a fix:
  a constant `+0.0` cannot reproduce a sign it does not know. Removed.

  **THE PLAN THESE KERNELS IMPLEMENT ALREADY SAID SO.** `PLAN-SV-PERF.md`
  §S1b, written before any of this work: "a dense row computes
  `1*a00 + 0*a01 + 0*a10 + 0*a11`, and `0.0 * (-x)` is `-0.0`, so the dense
  path maps some signed zeros to the opposite sign where the specialised path
  preserves them. Numerically identical; not bit-identical." It goes on to
  prescribe the exact test that was eventually re-derived after three wrong
  claims: "One test covering both classes should assert exactly that difference
  and nothing larger — equal under `==` everywhere, and `to_bits()`-equal
  everywhere the value is non-zero." That is
  `assert_matches_dense_up_to_signed_zero`, specified in advance and arrived at
  the long way.

  Two more places had it right: `kernels/apply_quad_perm.cu` documents it for
  the CUDA permutation kernels (and points back at `PLAN-SV-PERF.md`), and `apply_diagonal_1q` states it exactly for the 1q
  case, and `the_diagonal_path_differs_only_in_the_sign_of_zero` pins it
  with a warning to anyone who "tightens the oracle back to `to_bits()`" —
  which is precisely what the 2q tests did, in the same file. The true contract
  is now stated once on `diagonal_2q`, the three 2q tests are
  renamed to the house convention, and all of them run adversarial fixtures
  (negative neighbours next to signed zeros) that the original full-mantissa
  fixtures could not distinguish.

  **There is no exception — not even the permutations, and that was a THIRD
  wrong claim.** `apply_swap_ordered` and `apply_cx` compute nothing, which is
  true and irrelevant: the difference comes from the region a kernel does not
  WRITE, not from arithmetic in the region it does. SWAP fixes |00> and |11>,
  CX fixes the control-zero half, the dense path writes those, and the write
  normalises `-0.0`. The rule is about skipped WRITES, not multiplication.

  Found within seconds of making the contract mechanical instead of prose —
  which is the actual lesson. Fault injection proves a check is LOAD-BEARING;
  it cannot prove the check is COMPLETE. The `+ 0.0` "fix" survived injection
  and was believed. What broke it was asserting the same claim on a sibling
  kernel and watching injection fail to fire there. So: **a caveat that applies
  to a class gets asserted on every member of the class, mechanically** —
  `every_2q_gate_differs_from_the_dense_scan_only_in_the_sign_of_zero` now runs
  the whole gate table, forward and derivative matrices, so a kernel added
  later is covered whether or not anyone writes a test for it.

  Consequence, already handled: `tools/biteq` sees these differences by
  construction, and `diff.py` classifies them as dispatch artefacts rather than
  divergence.

* **[DONE]** Final measurement, n=22, best-of-5, warmed and interleaved, with
  the dense baseline carried IN-RUN by two control arms no dispatch can claim
  (agreeing to 0.3%):

  | gate | fast path | vs control ~1.61 ms |
  |---|---|---|
  | `cz` | 1.274 ms | 1.27x |
  | `crz` | 1.241 ms | 1.30x |
  | `swap` | 1.188 ms | 1.36x |
  | `rbs` | 1.182 ms | 1.36x |
  | `cy` | 1.061 ms | 1.52x |
  | `cu3` | 1.028 ms | 1.57x |

  Memory-bandwidth bound at this width, so what pays is not touching memory:
  the arms that skip half the state (`cy`, `cu3`) lead, and the diagonal — 16
  multiplies and 12 adds down to 4 multiplies — buys 1.3x, not the 4x its flop

  **The first version of this bench reported a 2.5x REGRESSION** for what is a
  speedup: `cz` ran first and absorbed the first-touch page-fault cost of a
  64 MB allocation. Three defences now, and the third came from review:

### 2.2 Metal per-shot trajectories — MEASURED 2026-08-25, and the item was mis-framed

**Status: live, confirmed in code** — `omega-backend-statevector-metal/src/lib.rs:1190`
delegates wholesale to the CPU statevector backend when `shots.is_some()` and
the circuit contains any `Reset`.

**The measurement does not answer the question the item asks, because the
question was wrong.** The pre-registered rule was "if delegation is within ~2x
of native Metal this is a documentation item; an order of magnitude and it
blocks QEC benchmarking on a Mac". Measured on an M5 Max, 6-layer H/CX/RZ
circuits, matched pairs differing only in whether `Reset` is present:

| n | shots | CPU no-Reset | Metal no-Reset | Metal WITH Reset (delegated) |
|---|---|---|---|---|
| 16 | 16 | 0.03 s | 0.02 s | 0.26 s |
| 16 | 4096 | 0.01 s | 0.03 s | **56.6 s** |
| 20 | 4096 | 0.06 s | 0.05 s | **300.0 s** |
| 22 | 64 | 0.48 s | 0.22 s | 30.7 s |

*(n=22 at 512/4096 was not run — the sweep hit a 10-minute cap. Reported
rather than extrapolated.)*

Two facts, and they point opposite ways:

1. **Metal-vs-CPU is only ~1.2-2.2x** on the path that actually reaches the
   GPU. That is the ENTIRE prize for fixing the delegation, and by the
   pre-registered rule it lands in "documentation item" — *a fortiori*, since
   a real per-shot GPU trajectory carries overhead this bound ignores.
2. **The delegated path costs ~13.8 ms/SHOT, flat**: 16.25 / 13.12 / 13.79 /
   13.88 ms/shot at 16 / 64 / 512 / 4096. Linear in shots. The non-Reset path
   is 0.01 s at 16 shots and 0.01 s at 4096 — it evolves ONCE and samples.

So the cost is not "CPU instead of GPU". It is **one full circuit
re-simulation per shot**, which is what a Reset in shots mode requires on ANY
backend. Fixing the Metal stall would buy the ~1.5-2x of item 1 and leave the
~1000x of item 2 untouched, because a Metal-native per-shot trajectory still
simulates the circuit once per shot — just ~1.5-2x faster each time.

**Revised conclusion.** The Metal stall is a small-prize item, correctly
deprioritised. The real item, which no document currently states, is: *Reset in
shots mode is O(shots x circuit) on every backend, while everything else is
O(circuit).* At n=20 / 4096 shots that is five minutes versus 60 ms. Anyone
benchmarking QEC on any backend hits this, not just on a Mac.

Whether that is fixable is a separate question and out of scope here — a
deferred-measurement / density-matrix path would avoid per-shot trajectories
for some circuits, and `PLAN-P2-DEFERRED-MEASUREMENT.md` in the handoff area is
the obvious place to look first. **Do not start it from this entry**; measure
what fraction of real QEC circuits admit deferral before assuming the fix
generalises.

**Method note.** The pre-registered threshold did its job in an unexpected way:
it was set on the wrong axis, and having it written down in advance is what made
that visible rather than letting the 1.2-2.2x be quietly reported as a
disappointing result for a question nobody re-examined.

### 3b.1 MPS analytic expectation densifies — CPU — **DONE 2026-08-27**

**One bug, not the two the report describes.** `--backend mps --expectation Z0`
on `ghz_31` (31 qubits, 31 gates, **bond dimension 2** — the least entangled
non-trivial circuit there is) took **1 479 s** on a Xeon and **refused** on
macOS/arm64. The reporter suspected "a representation collapse rather than a
slow contraction" and was right.

Root cause, confirmed at source: `MpsBackend::expectation` called `self.execute()`
with `shots: None`, took the resulting `ExecResult::Statevector`, and evaluated
`expectation_pauli` over the **dense 2^n vector**.

The two platforms differed only in whether the memory guard fired:

* macOS — 2.8 GiB free, guard trips, refuses in milliseconds naming the reason.
* Xeon — 314 GB free, guard passes, so it builds a **32 GiB** dense statevector
  for a χ=2 state and spends 25 minutes doing it.

So the macOS refusal was the system working, and the Linux runtime is what a
missing guard looks like.

#### Scope: performance and memory, NOT correctness

**The READOUT densified. The EVOLUTION did not.** `MpsBackend::execute` was
always evolving a genuine truncated MPS under a real bond cap, with the
`discarded_weight` / `fidelity_estimate` / `max_bond_reached` signals live and
the truncation certificate gating the result. Only the last step — turning that
chain into a number — went through `2^n`.

That distinction is the whole difference between a slow answer and a wrong one,
and it decides what downstream repos must do:

* **The numbers were right the entire time.** Every value this path returned is
  the value the contraction now returns — verified below to 10 decimal places.
* **MPS-vs-statevector cross-checks built on it stay valid.** They were
  comparing a truncated MPS against an exact statevector, which is what they
  claimed to compare. They were *not* comparing statevector against itself.
* **Nobody should delete MPS coverage on the strength of this item.**

This paragraph exists because a peer read the first draft's "the MPS is never
contracted as an MPS", drew the stronger conclusion, and was one `grep` of
`MPS_BOND_DIM` away from writing "my differential fuzz has been comparing
statevector to itself" into their own TODO and retiring real coverage. The
sentence was true of the readout and false as a summary. A finding that
overstates its blast radius costs more than one that understates it: the first
deletes working tests, the second only delays a fix.

#### Fix, as landed

`Mps::contract_product_operator` (`mps.rs`) — a left-to-right environment sweep
carrying `L[l,l']` between ket and bra bonds. `O(n · χ³)` time, `O(χ²)` live
memory, no densification anywhere. `Mps::expectation_product` normalizes by the
same sweep run with identity operators, which is `norm_sqr()` by construction
(pinned) but avoids `right_environments()`' all-`n`-environments-live
allocation. `MpsBackend::evolve_for_analytic` is the shared prologue; both
`expectation` and `expectation_multi` use it, so the multi door evolves the
chain once and contracts each observable against the same tensors.

`capacity::check_dense` is **kept** on the `ExecResult::Statevector` branch,
which still genuinely materialises `2^n`. Verified: `--backend mps --statevector`
at 31 qubits still refuses with the same message. The guard was narrowed to the
path it describes, not removed.

Two things found on the way, both fixed here:

* `expectation_multi` did **not** call `reject_reset_in_analytic_mode` while
  `expectation` did — so the same circuit and observable gave a refusal through
  one door and a single trajectory reported as analytic through the other. Same
  gate now on both.
* A Pauli string is a sparse *list* and nothing in `Observable` forbids it
  naming a qubit twice. The dense readout applied entries in order, making
  `Z₀Z₀` the identity; a per-site table that assigned rather than composed would
  have made it `Z₀`. Composed, and pinned.

#### Measured (this box, macOS/arm64, release)

| case | before | after |
|---|---|---|
| `ghz_31` ⟨Z₀⟩ | **refused** (needs 32.0 GiB, 2.5 GiB free) | **0.00 s**, `0.0000000000` |
| `ghz_31` ⟨Z₀Z₃₀⟩ | refused | 0.00 s, `1.0000000000` |
| `ghz_200` ⟨Z₀Z₁₉₉⟩ | impossible — `2^200` amplitudes do not exist | 0.00 s, `1.0000000000` |
| 20q brickwork d=14, χ=256, ⟨Z₀Z₁⟩ | — | `0.2443290927` vs statevector `0.2443290927` |
| same, expectation vs 4096 shots | — | 0.92 s vs 1.45 s — *cheaper* than sampling |
| 40q GHZ χ=2, in-crate test | dense guard refuses | 0.01 s |

Acceptance from the original plan, item by item: ms on macOS ✓ (Linux

### 3b.2 pauliprop — hard ceiling, and a certificate nothing consults — CPU

Two defects that must be read together. `--backend pauliprop --expectation Z0`
on a depth-16 HEA refuses at a **hardcoded 2^21 term ceiling** (~80 MB on a
314 GB host — three orders of magnitude below capacity), and `--truncate C`, the

or of the wrong sign. Reproduced at 31q/64q/128q by the reporter, all depth 16;
**reproduced here at 20q, which confirms it is depth, not width** — 20 qubits

#### CORRECTION: the certificate already exists — retracted 2026-08-27

The report says `--truncate` returns "wrong values with **no accuracy signal
whatsoever**", and §3b.2 repeated that phrase. **The second half is false**, and
R1 as originally written would have built a thing that is already there.

`omega-backend-pauliprop` has carried `PauliSum::dropped_mass` (`pauli.rs:321`)
— the L1 mass of truncated coefficients — accumulated at `pauli.rs:545`,
returned by `expectation_with_budget` at `sim.rs:297`, written onto the result
at `sim.rs:767/789/860`, described in this repo's own words at `sim.rs:57` as
"the **CERTIFIED** error bound", and **printed by omega-cli** at `main.rs:1408`

## 3c. Fermionic circuits — Majorana Propagation (NEW, 2026-08-28)

Requested: fermionic circuit support, with Pauli-propagation-style methods as
the suspected right approach, cross-referenced against Qiskit and the AQIS 2026
programme. That suspicion is correct and the method has a name.

### 3c.0 Two different asks, and they were conflated

The first draft of this section went straight to Majorana Propagation. That
answered "how do we simulate fermionic circuits that are too hard to simulate",
and skipped "can we express and run a fermionic circuit at all". The second
question is smaller, pays off sooner, and most of it is already built here.

Three tiers, and **only the third is Majorana Propagation**:

| tier | what | cost | when it is the right tool |
|---|---|---|---|
| **T1** | fermionic **surface** — operator IR, mappers, gate constructors, over the backends we already have | small | always; nothing else is usable without it |
| **T2** | **fixed-particle-number sector** statevector — the FQE/ffsim representation | medium, new backend | exact reference-grade runs, and the big win |
| **T3** | **Majorana Propagation** (§3c.1–3c.6) | large, new backend | approximate, when even the sector is too big |

### 3c.0a What is ALREADY here — more than the first draft said

`GateKind::RBS` **is the Givens rotation**, and its own doc says so:

> *"Reconfigurable Beam Splitter / Givens rotation: `RBS(θ) = exp(−i·θ/2·(Y⊗X −
> X⊗Y))`. **Hamming-weight preserving**; the primitive of butterfly / unary QML
> circuits."*

Hamming-weight preserving is exactly the property the fermionic gate set is
defined by. **Coverage, corrected 2026-08-28 after review — the first draft of
this line was wrong in three ways:**

| | RBS executes | adjoint / grad |
|---|---|---|
| statevector CPU | yes | yes (4-term Givens shift, `gradient.rs:523`) |
| statevector Metal | yes | yes |
| statevector CUDA | yes | yes |
| **statevector OpenCL** | **REFUSES** — `execute.rs:231-241`, falls back to CPU | refuses (`adjoint.rs:326`) |
| MPS | yes (`sim.rs:1274`) | **none — the MPS crate has no adjoint at all** |

The draft named OpenCL (the one GPU backend that does *not* support it),
omitted CUDA (which does), and claimed an adjoint uniformly when MPS has none.
Already documented in-tree at `LIMITATIONS.md:29-42` and
`BACKEND_FEATURE_PARITY.md:44` — an A3: the correct statement existed and was
not consulted.

The 2-qubit block rotation itself **is** done and correct — the matrix equals
`exp(−iθ/2(Y⊗X − X⊗Y))`, verified numerically, with a Lean proof at
`proofs/lean4/QuantumProofs/Rbs.lean`. But "the Givens rotation is done"
overstates it in one more way: **`RBS` is the ADJACENT-mode gate**. A fermionic
Givens rotation between non-adjacent JW modes needs a Z-string or a swap
network, and T1 must specify which. That routing is not in the repo and was
not in this plan.

The `middle_block_2q` detector added in 3b.1 is *related* but the first draft
overstated the identification. It requires `g[0] == 1 && g[15] == 1`
(`sim.rs:1334-1353`) — **identity** on `|00⟩` and `|11⟩`. The general
number-preserving two-qubit gate is (phases on the corners) ⊕ (U(2) on the
middle block), so fSim, Givens-with-phase `G(θ,φ)`, and `XXPlusYY` with `β ≠ 0`
all return `None`. Pure corner phases are caught separately by `diagonal_2q`;
a gate with *both* nontrivial corner phases and a middle rotation is caught by
neither and runs dense. So the sparse dispatch knows a **subset** of the
number-preserving block — and notably not `CPhase`, the very gate above.

What is missing is the layer above:

* a fermionic operator IR (`a†_p a_q` sums with coefficients, normal ordering);
* **Jordan–Wigner** / Bravyi–Kitaev / parity mappers to `Observable`;
* orbital rotation as a composite (brickwork of Givens + a phase layer — the
  standard decomposition, and the one ffsim uses);
* ~~a **controlled-phase** gate~~ — **RETRACTED. This was not a gap.** The
  identity `exp(iθ n_p n_q) = diag(1,1,1,e^{iθ})` is right, but the operator is
  already parseable and executable: `omega-parser/src/lower.rs:1309-1333`
  lowers `cp` / `cu1` / `cphase` to `CU3(0,0,λ)`, which *is*
  `diag(1,1,1,e^{iλ})`, and the statevector's diagonal fast path names
  "CU1/CPhase" explicitly (`sim.rs:982-999`). What T1 needs is a
  **constructor** emitting `CU3(0,0,θ)` — a one-liner. A dedicated `GateKind`
  variant is ergonomics, not a blocker. Another A3.

So T1 is genuinely a *layer*, not a rewrite: it lowers fermionic constructs onto
gates the backends already execute.

### 3c.0b T2 — the fixed-particle-number sector, and why it is the real prize

A fermionic circuit that conserves particle number and `S_z` never leaves the
`(N_α, N_β)` sector, whose dimension is `C(N, N_α) · C(N, N_β)` rather than
`4^N`. Computed here:

| orbitals | qubits | filling | dense `2^2N` | sector dim | ratio | dense | sector |
|---|---|---|---|---|---|---|---|
| 8 | 16 | 4+4 | 65 536 | 4 900 | 13× | 1.0 MiB | 76.6 KiB |
| 16 | 32 | 8+8 | 4.29e9 | 1.66e8 | 26× | **64.0 GiB** | **2.5 GiB** |
| 20 | 40 | 10+10 | 1.10e12 | 3.41e10 | 32× | 16.0 TiB | 508.6 GiB |
| 32 | 64 | 4+4 | 1.84e19 | 1.29e9 | **1.4e10×** | **256.0 EiB** | **19.3 GiB** |

Rows **2 and 4** reproduce ffsim's published numbers exactly (64 GiB → 2.5 GiB
at 16 orbitals; 256 EiB → **19.3 GiB** at 64 qubits, 1/8 filling) — an
independent check that the representation is understood rather than paraphrased.
(The draft said "the last two rows"; row 2 is not one of them.)

The ratio is **13–32×** across the half-filled rows above — the draft said
"13–40×" and 40× appears nowhere in the table; it would need ~26 orbitals. The
win is astronomical only away from half filling. **It is not uniform**, and the
draft's "dilute is where chemistry actually sits" is too strong: active-space
calculations routinely sit near half filling, and dilute is the full-orbital
picture. Quoting only the 1.4e10× row would be overselling.

### 3c.0c References — TWO ROLES, and they are not the same library

"What do we compare against" is two questions, and conflating them is how a
project ends up checking its results against the code it copied its algorithm
from. Keep them separate on purpose:

* **Result oracle** — run the same circuit, compare the numbers. Wants
  *independence* above all; speed and readability are irrelevant.
* **Algorithm reference** — source read while implementing (Givens
  decomposition, sector addressing, mapper conventions). Wants *clarity* and a
  **compatible licence**; its numerical output never enters our test suite.

**A library used as the algorithm reference is disqualified as the primary
result oracle for the same component.** If we implement orbital rotation by
reading ffsim's Givens decomposition, then ffsim agreeing with us on orbital
rotation is close to self-agreement. That is why two independent emulators
matter rather than one good one.

Licences, checked: this repo is **Apache-2.0** (`LICENSE`, and 230 `SPDX-License-Identifier: Apache-2.0`
headers). ffsim, OpenFermion-FQE, OpenFermion, Qiskit Nature and PySCF are
**all Apache-2.0**. So all four are readable as algorithm references without a
licence problem — which is not automatic and was worth checking before
planning to read any of them.

| | role | licence | why |
|---|---|---|---|
| **ffsim** `arXiv:2605.03123`, IBM Quantum | **algorithm reference** (primary) + secondary oracle | Apache-2.0 | Clearest source for the Givens/orbital-rotation decomposition and the number-preserving gate set. Qiskit-integrated, so it is also the cheapest oracle to wire. |
| **OpenFermion-FQE** Quantum **5**, 568 | **result oracle** (primary) | Apache-2.0 | Separate addressing scheme, separate orbital-rotation algorithm (LU vs Givens). The independence that makes agreement mean something. |
| **Qiskit Nature** 0.8.0 (Jun 2026, community-maintained) | **algorithm reference** for MAPPERS | Apache-2.0 | `JordanWignerMapper` / `BravyiKitaevMapper` / `ParityMapper` and `FermionicOp` — the mapper conventions, which are where sign errors live. |
| **PySCF** FCI | ground truth (energies) | Apache-2.0 | Not a circuit simulator. The only reference that is not itself a quantum simulator. |
| **Qiskit Aer** | dumb oracle, `N ≤ 14` | Apache-2.0 | Already gated in `ci.sh`. Cannot reach interesting sizes — that is the point of the others. |

So the assignment is: **read ffsim + Qiskit Nature, check against FQE + PySCF.**
Not the other way round.

### 3c.0d The wire problem — a concrete blocker, found before it cost anything

`omega-bridges` speaks **QASM2 over JSON** (`runner_io.py`, "STDOUT IS THE
WIRE"). **`RBS` has no QASM2 spelling** — `every_emitted_gate_is_readable.rs`
marks it `Spec::NotQasm2`, "Givens rotation; no qelib1 spelling".

And decomposing it does not help, it actively breaks the comparison: ffsim
parses a Qiskit circuit only when every gate is Hamming-weight preserving and
*recognisable as such* (`CPhaseGate`, `SwapGate`, `XXPlusYYGate`). Lower `RBS`
into CX + rotations and ffsim rejects the circuit — or worse, falls back to a
general simulator and we compare against the thing we were trying to avoid.

~~The repo already has the answer: a **QPY lane**~~ — **RETRACTED, and this
retraction is the sharpest instance of the very trap this subsection is about.**

A QPY lane does exist (`qiskit_runner.py:608 _qpy_to_qasm2`, `:681
_qasm2_to_qpy`) but its ingest is `qasm2.loads` → `qpy.dump`. It is a
**QASM2↔QPY converter**, so its input wire is exactly the QASM2 that cannot
spell `RBS`. It can never produce a QPY blob containing `XXPlusYYGate` from an
omega circuit. Only the decode half and the base64/JSON plumbing are reusable.

**The ffsim bridge is net-new**, all of it: a `requirements-ffsim.txt` and
venv, a runner mode, and a circuit-emission path that is either a Rust-side QPY
writer or a JSON gate-list consumed by a Python `QuantumCircuit` builder. Note
also that **ffsim appears nowhere in this repo** — not installed, not
required, not referenced outside this plan. §3c.0e's "do it *with* T1" stands,
but not because it is mostly plumbed.

#### The gate mapping, verified numerically rather than assumed

The draft said `RBS(θ) → XXPlusYYGate`. **That is wrong**, and wrong in the
worst available way: the result is still Hamming-weight preserving, still
accepted by ffsim, and a different unitary. Checked against qiskit 2.5.2 in
this repo's own `.venv-qiskit`:

```text
RBS(θ)  =  XXPlusYYGate(2θ, β = +π/2)      ==  XXPlusYYGate(−2θ, β = −π/2)
RBS(θ)  ≠  XXPlusYYGate(θ)                 (default β = 0, and half the angle)
```

Both the **angle doubling** and the **β phase** were absent. `XXPlusYYGate(θ)`
with default `β = 0` carries `−i·sin` off-diagonals where RBS carries real
`±sin`. A bridge built on the draft's mapping would have run, agreed on
Hamming weight, and disagreed on every number — with no error anywhere.

`CPhase → CPhaseGate` and `Swap → SwapGate` still need the same numerical
check before use; neither has had one.

The general lesson stands and now has a receipt from inside its own section:
the obvious path produces a comparison that looks like it works and silently
measures the wrong thing — and so does an unverified gate mapping.

### 3c.1 Why Majorana Propagation and not "just Jordan–Wigner it"

The obvious cheap path is: map the fermionic problem to qubits with
Jordan–Wigner and feed the existing `omega-backend-pauliprop`. That is
**correct and useless**, and the reason is the paper's central claim.

Majorana monomials do not map to local Pauli strings. Under a fermion-to-qubit
transform they become *"generally mapped to non-local Pauli strings, with Pauli
weights spanning a wide range, even for fixed Majorana monomial length"*. So:

> *"previous guarantees for PP with weight truncation do not apply to Fermionic
> systems, as Pauli weight does not capture typical operator dynamics."*

`--max-weight` is pauliprop's main structural lever, and after JW every term
looks heavy. The truncation axis survives syntactically and dies semantically —
which is precisely the failure shape §3b.2 is about: a knob that still runs and
no longer means anything.

MP replaces Pauli weight with **Majorana monomial length** `w = ‖b‖₁`, and the
paper's contribution is showing that length is the right truncation axis: high-
length monomials are exponentially unlikely to contribute to expectation values,
and backflow from high to low length is quadratically suppressed.

**Both paths get built anyway** — see §3c.4. JW→pauliprop *untruncated* is
exact, so it is the in-tree differential oracle for MP. The cheap path's value
is as an oracle, not as the product.

**Consequence for the API, and it is not optional.** A knob that survives
syntactically and dies semantically is *worse* than one that breaks, because
`--max-weight` keeps accepting values and keeps producing numbers. That is the
identical shape as `dropped_mass` being computed and consulted for nothing
(§3b.2), one level up: the mechanism intact, the meaning gone.

So when MP lands, **`--max-weight` on a fermionic circuit must refuse**, not
quietly mean something else — the same posture as the truncation gate. A user
who reaches for the Pauli-weight lever on a fermionic problem has to be told the
axis does not apply, and pointed at `--max-length`. Anything softer reproduces
the defect this whole batch of work exists to remove.

### 3c.2 The algebra, and why it maps onto the engine we own

An `N`-mode system gives `2N` Majorana operators, `m_{2j-1} = a_j† + a_j`,
`m_{2j} = i(a_j† − a_j)`, with `{m_i, m_j} = 2δ_ij` and `m_i† = m_i`. A monomial
is indexed by a **`2N`-bit vector** `b`:

    M_b = i^{r_b} · m_1^{b_1} m_2^{b_2} ⋯ m_{2N}^{b_{2N}},     w = ‖b‖₁

`r_b` is the Hermiticity phase: `0` when `w` or `w−1` is a multiple of 4, else
`1`. The `4^N` operators `{M_b}` span the whole operator space.

Circuits are `U(θ) = Π_j exp(−i θ_j M_{b_j} / 2)`, and the propagation rule is

    M_b  --exp(−iθ M_c/2)-->  cos(θ)·M_b + sin(θ)·i M_c M_b     (anticommuting)
    M_b  --exp(−iθ M_c/2)-->  M_b                               (commuting)

**That is `branch()` in `omega-backend-pauliprop`, with a different algebra
underneath.** The mapping is close to mechanical:

| pauliprop | majoranaprop |
|---|---|
| `PauliKey` — `(x \| z)` word pair | `MajoranaKey` — one `2N`-bit word array |
| Pauli weight | monomial **length** `w = popcount(b)` |
| symplectic commutation test | commute iff `w_a·w_b − \|a ∩ b\|` is even |
| Pauli product + `i` phase | XOR of vectors + transposition-parity sign |
| `is_all_iz()` readout | **paired** test (§3c.3) |
| `coeff_min` / `max_weight` / `max_freq` | same three, `max_weight` → `max_length` |
| `dropped_mass`, `max_terms` | **unchanged** |
| `PauliSum` support-skip optimisation | same idea on the `2N` vector |

The commutation rule is the one piece worth deriving carefully rather than
copying: exchanging `M_a` and `M_b` costs `w_a·w_b` transpositions, of which the
`|a ∩ b|` shared operators contribute `+1` rather than `−1`, giving sign
`(−1)^{w_a w_b − |a∩b|}`. It is a **three**-popcount test (`w_a`, `w_b`,
`|a∩b|`) — the draft said two and called it cheaper than the symplectic test,
which needs two; both are trivially cheap and the comparison was decoration.
What matters is that an off-by-one here silently flips the sign of half the
terms, so it gets an exhaustive small-`N` test against explicitly built
matrices, not a spot check.

**`max_freq` is listed as carrying over, and that is asserted rather than
argued.** Split frequency is defined by pauliprop's own branch semantics
(`pauli.rs:266`); whether MP has a meaningful frequency axis is not
established here. The paper's small-angle truncation suggests it does, but
that must be checked before the column is trusted.

### 3c.3 Readout — the part with no pauliprop analogue

`f(θ) = Σ_b c_b(θ) · Tr[ϱ M_b]`. On a Fock basis state, `Tr[ϱ M_b] ≠ 0` **iff
the monomial is *paired*** — for every mode `j`, bits `2j−1` and `2j` are either
both present or both absent. Unpaired monomials contribute exactly zero.

This replaces `is_all_iz()`. It is also a cheap early filter: an unpaired
monomial can never contribute, though it can still *branch into* one, so it
cannot be dropped during propagation — only at readout. Getting that wrong is a
silent wrong-answer bug of exactly the class §3b.2 documents, so the test is
"pruning unpaired terms early changes the answer" asserted as a disagreement,
in the `skipping_identity_sites` shape.

**Two gaps here, both flagged in review and both real:**

1. **The readout VALUE is not written down**, only the `≠ 0` criterion. For a
   paired monomial the value is a product of `±(1 − 2n_j)` factors corrected by
   `i^{r_b}` and the operator ordering — and that correction is exactly where a
   sign bug will live. It must be derived and pinned before P0 is called done.
2. **Non-Fock initial states are not covered at all.** `is_all_iz()` is a
   `|0…0⟩` readout; MP needs an arbitrary Fock (Hartree–Fock) reference, and a
   state prepared *by an orbital rotation* is not a Fock state, so the paired
   rule does not apply to it. P0 must say what the reference state may be.

### 3c.4 Validation ladder

Four independent references, in increasing order of what they cost to build:

1. **Dense Fock-space oracle.** Build the `2^N × 2^N` matrix of `M_b` explicitly
   for `N ≤ 6` and contract. Slow, obviously correct, and the only reference
   that tests the *algebra* rather than the pipeline. Covers the sign
   conventions, the Hermiticity phase `r_b`, and the paired-readout rule.
2. **JW → existing `omega-backend-pauliprop`, untruncated.** Two engines in this
   repo reaching one number by different routes. Free, because both already
   exist once the JW mapper does.
3. **Qiskit Nature** — `FermionicOp` + `JordanWignerMapper`, through the
   existing bridge harness (`crates/omega-bridges/python/`). External oracle,
   same pattern as the qiskit arm already gated in `ci.sh`.
4. **QuEra `ppvm`** — already bridged (`ppvm_runner.py`), and already used
   precisely because *"it implements the SAME ALGORITHM as
   omega-backend-pauliprop independently"*. It has no Majorana engine, so it
   anchors leg 2, not MP itself.

Legs 1 and 2 are mandatory before any performance claim. Leg 3 follows the
existing venv/skip discipline — and note `ci.sh` already treats an unbuilt venv
as a skip that reads as a pass, which is what its closing line exists for.

### 3c.5 Qubits too — symmetry merging attacks the §3b.2 defect directly

`arXiv:2512.12094` (Teng, Chang, Rudolph, Holmes) is an upgrade to the qubit
engine we already ship: when a circuit has a symmetry, many Pauli strings evolve
redundantly, so merge each symmetry orbit and propagate one representative.
Space drops by the orbit size; the authors report **improved stability
specifically under truncation and noise**, benchmarked on all-to-all Heisenberg
dynamics.

That last clause is why it belongs here rather than in a wishlist. §3b.2
measured `dropped_mass` going vacuous — 1.4e+03 on a quantity in [−1, 1] —
because term count explodes and truncation gets aggressive. Fewer terms for the
same physics means a tighter budget for the same cutoff. **Symmetry merging is a
fix for the vacuity, not just a speedup**, on the symmetric circuits where it
applies (translation, permutation).

Ordering consequence: it lands *after* §3b.2 R1, because R1's certificate is how
the improvement gets measured. Without an informative budget there is no way to
show merging tightened anything.

### 3c.6 Phasing, and the honest cost

* **P0 — algebra + oracle (no engine).** `MajoranaKey`, product, commutation,
  length, Hermiticity phase, paired readout, and the dense `N ≤ 6` oracle.
  Nothing user-facing. Everything after this is worthless if this is wrong, and
  it is the only part where a sign error hides.
* **P1 — JW mapper + `FermionicOp`-equivalent IR.** Buys validation leg 2, and
  is independently useful: the repo currently has **no fermionic surface at
  all** — `Observable::parse` speaks only `X/Y/Z` + index, and the sole
  Bravyi–Kitaev hits in the tree are magic-state distillation, unrelated.
* **P2 — `omega-backend-majoranaprop`.** The engine, forked structurally from
  pauliprop, inheriting `dropped_mass` / `max_terms` / the R1 certificate and
  gate. `max_weight` becomes `max_length`.
* **P3 — the a-priori bound. DO NOT PLAN AROUND THE FORMULA AS TRANSCRIBED
  IN THE FIRST DRAFT.** MP has something pauliprop does not — Theorem 1 bounds
  the error *before the run*, so the certificate could carry a predicted bound
  beside the measured dropped mass, with the two disagreeing as its own bug
  signal. Genuinely stronger than the qubit engine's certificate.

  But the draft's transcription — `Δ/E‖O‖² ≤ 1/2^{N−1} + (e·w₀/N)^{w₀/2}` —
  **is not a well-formed quantity as written**, and garbles a
  mean-squared-error ratio over an ensemble. The decay is also regime-limited:
  `(e·w₀/N)^{w₀/2}` shrinks in `w₀` only while `w₀ < N/e`, so "decays
  exponentially in the cutoff" is not unconditional. **Re-derive from the paper
  before P3 is planned around it.**
* **P4 — benchmark.** The paper's Table I is 28/40/52 modes: MP pre-process
  0.05 / 1.34 / 13.85 s and per-estimate 0.0009 / 0.0395 / 0.1092 s, against
  CUDA-Q MPS at 32.15 min / 10.10 h / >24 h, with MP also ~200× more accurate at
  28 modes (1.39e-2 mHa vs 2.71 mHa). **We have an MPS backend in-tree**, so
  that is the same comparison run natively — the strongest available check that
  our MP is doing what theirs does, and it reuses the MPS-vs-pauliprop
  comparison the repo already performs on qubit circuits.

**Cost honestly:** P0–P2 is the bulk and is a new backend crate, not a patch.
P3 is small once P2 exists. P4 depends on a chemistry ansatz generator the repo
does not have. Do **not** start P2 before §3b.2 R1 lands — MP inherits that
certificate, and building the engine first means building it twice.

## 3d. Qudits — same methodology as §3c

Tier the work, state what already exists, split the result oracle from the
algorithm reference, and find the blockers before they cost anything.

### 3d.0 What exists here: nothing, and that is the honest answer

`grep -riE 'qudit|qutrit|ququart' crates/ --include='*.rs'` returns **zero**
relevant hits. There is no qudit surface, no `d`, and no per-register
dimension: `CircuitIR` carries a scalar `num_qubits: u32`
(`omega-core/src/circuit.rs:249`).

What *does* exist is a precedent worth naming, because it is easy to mistake
for support: the photonics and CV backends carry a non-binary local dimension
(Fock occupation per mode). That is **bosonic** — unbounded occupation with a
cutoff — not a qudit, which is a fixed `d`-level system. The machinery does not
transfer; only the reassurance that the codebase is not structurally
qubits-only.

### 3d.1 The blast radius, measured rather than guessed

Dimension 2 is not a parameter here, it is an assumption compiled into the
addressing:

**The first version of this table was fabricated, and it is corrected here
rather than silently replaced.** It reported 62 / 4 / 23 / 69; **none of the

**The conclusion survives the recount: MPS is the cheaper path to qudits, not
statevector.** The statevector backend is built on `1 << q` masks — 71 sites of
genuine rewrite — and that is why "add qudits to the statevector backend" is
the wrong first move despite being the obvious one.

But "generalises **unchanged** / carries over **untouched**" was overstated, in
three specific ways:

* **True and verified:** the SVD kernel is genuinely dimension-generic —
  `truncated_svd_flat(matrix, m, n, stride, …)` (`svd.rs:87`) takes an
  arbitrary `m × n`, and nothing in `svd.rs` assumes `d = 2`.
* **Not unchanged:** gate signatures are **fixed-size array types** —
  `apply_2q(&[Complex64; 16])`, `pauli_matrix() -> [Complex64; 4]`. For `d > 2`
  the *type* changes, which ripples through `mps.rs`, `sim.rs`, the tests and
  the `Backend` plumbing. That is an API change, not a literal edit.
* **Not absent:** the MPS crate's own readout uses the same 2-adic addressing
  the argument holds against statevector — `(target_basis >> q) & 1`
  (`mps/sim.rs:1493`), and `to_statevector`'s "bit `q` of the basis index"
  (`mps.rs:531`).
* `MpsTensor` has **no `phys` field**; the dimension is implicit in
  `data.len()`, so "the tensor already HAS a `phys` index" was true of the
  indexing arithmetic and false of the struct.

Directionally right, magnitude understated by roughly an integer factor.

### 3d.2 Tiers

* **T1 — surface.** Per-register dimension in `CircuitIR`. This is the invasive
  part and it is a **core IR change**: `num_qubits: u32` becomes a dimension
  vector, and every backend must at minimum assert `all == 2` to keep working.
  Doing that assertion first, before any qudit backend, is what stops a
  qudit circuit silently running as a qubit one.
* **T2 — exact backend: MPS first** (§3d.1). Generalise `phys` from 2 to `d`,
  per-site `d` for mixed-dimensional registers.
* **T2b — statevector**, mixed-radix. Larger, and only worth it as the
  small-`n` oracle for T2.
* **T3 — methods.** Qudit **stabiliser** (Clifford over `Z_d`, clean for prime
  `d` — Gottesman), and **qudit Pauli propagation** over the Weyl–Heisenberg
  clock/shift group `X_d, Z_d` with `ω = e^{2πi/d}`.

  **The "same engine, different group" claim was too strong** and is split
  here into what carries and what does not:

  * **Carries.** The Heisenberg direction; `Weighted.coeff` is already
    `Complex64` (`pauli.rs:270`); the `is_all_iz` readout on `|0…0⟩`
    generalises (`⟨0|Z_d^k|0⟩ = 1`); and — checked, because the truncation gate
    depends on it — the `dropped_mass` **L1 bound survives**: Weyl operators
    are unitary with operator norm 1, so `|⟨W⟩| ≤ 1` still holds. The
    certificate and its vacuity gate transfer.
  * **Does NOT carry: the branch machinery, which is the hard part.**
    `PauliKey::anticommutes_with` (`pauli.rs:229-236`) is a **mod-2** symplectic
    parity — `acc & 1 == 1` over popcounts. Weyl operators **ω-commute**
    (`W₁W₂ = ω^k W₂W₁`), so the test is a mod-`d` symplectic form: a different
    function on a different key layout. And `BranchHook`
    (`sim.rs:78-88`) takes `(factor, cos, sin)` — a **two-child** split that
    exists only because `P² = I` for Hermitian Pauli strings. For `d > 2`,
    `X_d`/`Z_d` are non-Hermitian of order `d`, and conjugation produces up to
    **`d` children** with coefficients that are not `cos`/`sin`. The branch
    step, `map_one`/`map_two`, and the CUDA and Metal branch hooks that share
    that signature all get **redesigned, not re-parameterised**.

  Note also: qudit Weyl expectations are **complex**, not real. Anything
  reusing the certificate's `observable_range` reasoning outside the qubit
  Pauli group must re-derive the realness assumption, not just the bound.

## 3e. Circuit representation — do NOT invent a format

Asked before building: are there standards for this? **For qudits yes, for
fermionic circuits no — and the "no" is a design answer, not a gap.**

### 3e.1 Qudits — DITQASM is the de-facto standard, and it extends QASM 2

**OpenQASM 3 has no qudit support.** The spec is qubit-centric throughout;
nothing in it carries a per-register dimension. There is no ratified standard.

What exists is **DITQASM** (MQT Qudits, `arXiv:2410.02854`): *"an adaptation of
OpenQASM for describing mixed-dimensional quantum circuits and architectures"*,
which **extends the OpenQASM 2.0 grammar**. Three features, and each maps onto
something we would otherwise design badly:

* **register allocation carrying dimensionality** — exactly the `CircuitIR`
  change §3d.2 T1 needs;
* **gate-level description with control on arbitrary levels** — the part that is
  easy to get wrong, since a qudit controlled gate must name *which level*
  controls;
* hardware-agnostic representation.

That it extends **QASM 2** rather than 3 is the load-bearing detail for us: this
repo's parser, exporter, conformance suite and every bridge speak QASM 2. A
DITQASM lane is an extension of the grammar we already have, not a second
front-end.

Also in the space: **OpenQudit / Qudit Gate Language (QGL)** — symbolic gate
definitions, a compilation framework rather than an interchange format.

**Position: adopt DITQASM's register-dimension and level-control syntax rather
than inventing one.** Even if only a subset is implemented, matching an existing
dialect is what makes a differential harness against MQT Qudits possible at all
— and §3c.0d is the standing lesson on what a bespoke wire costs.

### 3e.1a DITQASM — adopt it, and what that costs concretely

Decision: **adopt DITQASM rather than invent a dialect.** Licence checked —
MQT Qudits is **MIT** (`LICENSE`, `pyproject.toml` `SPDX-License-Identifier: MIT`),
which is compatible with this repo's Apache-2.0 for reading as an algorithm
reference and for interoperating.

#### The syntax, from the project's own tutorial

```
DITQASM 2.0;
qreg field [7][5,5,5,5,5,5,5];
qreg matter [2];
creg meas_matter[7];
h matter[0] ctl field[0] field[1] [0,0];
cx field[2], matter[0];
rxy (0, 1, pi, pi/2) field[3];
measure q[0] -> meas[0];
```

Four things to notice, in increasing order of how much work they are:

1. **Header** `DITQASM 2.0;` in place of `OPENQASM 2.0;`.
2. **Per-qudit dimensions**: `qreg <name> [<count>][<d₁>,…,<d_count>];` — a
   second bracket group listing each qudit's dimension. Mixed dimensions are
   the normal case, not an edge case.
3. **`rxy(i, j, θ, φ)`** — a rotation in the two-level subspace `{i, j}` of one
   qudit. This is the fundamental qudit single-qudit gate and it is
   *parameterised by which two levels it acts on*. There is no qubit analogue;
   `Rx`/`Ry` are the `d = 2` special case with `(i,j) = (0,1)` fixed.
4. **Control on arbitrary levels**: `<op> <target> ctl <qudit>… [<level>…];` —
   a controlled gate must name **which level** of each control qudit activates
   it. This is the genuinely new statement form.

#### Cost against this repo's actual grammar

The parser is **pest** (`crates/omega-parser/src/qasm2.pest`), and the current
rule is:

```
qreg_decl = { "qreg" ~ ident ~ "[" ~ integer ~ "]" ~ ";" }
```

So item 2 is that rule plus one optional group —
`~ ("[" ~ integer ~ ("," ~ integer)* ~ "]")?` — and item 1 is a token. Those
are genuinely small. **Item 4 is not**: a new statement form with a trailing
level list touches the gate-application rule, the AST, and the lowering pass.

**Item 3 was overstated.** The draft said `GateOp`'s shape "does not express"
two level indices. It does: `params` is `SmallVec<[ParamExpr; 3]>`
(`circuit.rs:180`) — *variable* length, inline-3 spilling to heap — and
DITQASM's own concrete syntax `rxy (0, 1, pi, pi/2)` passes the levels
positionally in the parameter list. Four params fit today. The real gap is
**semantic**, and smaller: no `GateKind::Rxy` variant, no typed integer params,
and every consumer currently treats `params` as angles.

#### VERIFY BEFORE IMPLEMENTING — this is a paraphrase, not a spec

The block above is transcribed from MQT Qudits' **tutorial prose**, not from
their grammar. After the `RBS → XXPlusYYGate` error — where a mapping
transcribed from memory produced a plausible, accepted, silently wrong
unitary — the standing rule applies: **read MQT Qudits' actual parser/grammar
file before writing a line of ours**, and pin the result with round-trip tests
against `mqt.qudits` itself.

Specific unknowns, listed so they are not silently assumed:

* Does `qreg matter [2];` (no dimension group) mean *2 qudits of dimension 2*,
  or *one qudit of dimension 2*? The tutorial's `field [7][5,…]` pairs a count
  with 7 dimensions, which suggests the former — **unconfirmed**.
* Are `h` and `cx` on a qudit the *generalised* (Fourier / `X_d` shift) gates,
  or the `d = 2` embeddings? These are different operators and the name is the
  same.
* Whether the level list `[0,0]` after `ctl` is per-control-qudit (likely) and
  what the ordering convention is.
* Whether `DITQASM 2.0` is version-locked to OpenQASM 2 semantics elsewhere.

#### Position

Implement in the order the cost analysis gives: header + dimensioned `qreg`
first (small, and it is what §3d.2 T1 needs anyway — the IR must carry a
per-register dimension before any of this means anything), then `rxy`, then
level-controls. Each step round-tripped against `mqt.qudits` rather than
against our own reading of the tutorial.

### 3e.2 Fermionic circuits — CORRECTED: no *file format*, but a representation IS required

The first draft said *"the gate set IS the representation"* and *"no fermionic
circuit format, and there should not be one"*. **The second half of that
conflated two different claims and the conflation is wrong.** Corrected below,
because the repo itself is the counterexample.

#### What was right

There is no standard *interchange file format* for fermionic circuits in the
wild, and inventing one for interchange would be against §3e's own principle.
What **is** standardised sits either side of the circuit:

* **FCIDUMP** — one- and two-electron integrals, i.e. the *Hamiltonian*. Read
  by both PySCF and ffsim. This is what a fermionic problem is actually
  specified by.
* **QCSchema** — structured quantum-chemistry I/O.
* **OpenFermion** `FermionOperator` / `InteractionOperator` — the de-facto
  in-memory operator representation; Qiskit Nature's `FermionicOp`
  interoperates with it.

#### What was wrong, and why

The draft's argument was: *fermions can be mapped to qubits, therefore a
fermionic circuit is a qubit circuit, therefore no fermionic representation is
needed.* The inference from **can** to **should** does not hold, and **bosons
are the proof — inside this repo.**

A bosonic circuit cannot be lowered to qubits at all: Fock space is
infinite-dimensional and only a cutoff makes it finite. So this repo gave
bosonic its own circuit type and its own text form:

* `CircuitType { GateBased, Photonic }` — `omega-core/src/circuit.rs:241`
* `crates/omega-parser/src/opticqasm.pest` — a **separate grammar**, header
  `OPTICQASM 1.0;`, with `photon_decl` rather than `qreg`

Apply the draft's reasoning to bosons and it says "just lower photonics to
qubits", which is impossible. **The difference between fermions and bosons here
is about what is possible, not about what is correct** — and the draft
mistook the availability of a lowering for a reason to represent everything
post-lowering.

#### The concrete cost, in this plan's own terms

* **§3c's T2 — the fixed-particle-number sector backend, called "the real
  prize" — is fermionic-native.** It works in the `(N_α, N_β)` sector, not on
  qubits. A qubit-only IR cannot feed it, for exactly the reason a qubit-only
  IR cannot feed the photonics backend.
* **Lowering early destroys information T2 and the mappers need**: the mapping
  choice (JW vs BK vs parity), the orbital structure, and the particle-number
  sector. Once it is a `CX` ladder those are gone.
* **The reference implementations are fermionic-native, not circuit-based.**
  ffsim's core API is `ffsim.apply_orbital_rotation(vec, orbital_rotation,
  norb=norb, nelec=nelec)` — a function on a fermionic state vector — and its
  own docs call the Qiskit gate layer *"a secondary interface layer"*. FQE is
  fermionic throughout. Neither has a fermionic circuit file format, **and
  neither represents circuits as qubit gates internally.** The draft cited
  ffsim's Qiskit *parser* as evidence for a claim its *core* contradicts.

#### Corrected position

1. **An in-memory fermionic representation is REQUIRED**, mirroring `Photonic`:
   a `CircuitType` variant (or equivalent) plus fermionic ops indexed by
   *modes*, carrying orbital rotations and number–number interactions as
   first-class operations rather than as pre-lowered gates. §3c.0a already
   listed "a fermionic operator IR" as missing — that item is load-bearing, not
   a convenience.
2. **Lowering to qubits is a PASS, not the representation.** JW/BK/parity
   become selectable lowerings from the fermionic IR, which is also what makes
   §3c's validation leg 2 (JW → pauliprop, untruncated) possible.
3. **No new interchange file format for now.** Unlike qudits (DITQASM exists)
   and Majorana (Stim `MPP` exists), there is nothing external to adopt. If a
   text form is later needed, follow the **OPTICQASM precedent** — a small
   dedicated grammar beside the others — rather than a QASM dialect, and only
   when something actually needs to serialize.

**Standing correction:** "there is no standard format" and "no representation
is needed" are different claims. The first is true and checkable; the second
was an inference, was not checked, and is false.

### 3e.2a FermionicQASM 1.0 — the text form, mirroring OPTICQASM

**Searched before inventing, per §3e's own rule.** Results:

* **No fermionic QASM dialect exists.** The one candidate the search surfaced,
  `qiskit_cold_atom.fermions.FermiHubbard.qasm()`, is a *generic inherited
  method* — `FermiHubbard(FermionicGate) → Gate → Instruction`, with no `qasm`
  override — **deprecated** in qiskit-terra 0.25.0 ("no replacement will be
  provided") and **removed in Qiskit 1.0**. The draft fused those two lifecycle
  events into "removed in 0.25.0". Not a fermionic dialect either way. Nothing
  else: not in OpenQASM 2 or 3, not cQASM, not Jaqal.
* **The name `FermionicQASM` is unused.** No prior art found.
* **OPTICQASM is in-house.** It appears in this repo's docs and nowhere
  external, so the bosonic precedent is *"we wrote one"*, not *"we adopted
  one"*. That makes writing a fermionic one consistent with precedent rather
  than a departure — and it also means neither carries the authority of a
  standard, which should be said out loud in both.

So: **invent, but adopt every established CONVENTION**, since those exist even
though the format does not.

#### Conventions adopted from elsewhere (not invented here)

* **Wire = fermionic MODE**, from `qiskit-cold-atom`: *"the wires of a quantum
  circuit describe the occupations of individual fermionic modes"*, each mode
  empty `|0⟩` or occupied `|1⟩` by Pauli exclusion.
* **Spin ordering**: spin-½ fermions in `N` spatial modes are `2N` wires, *the
  first `N` spin-up and the last `N` spin-down*. This is qiskit-cold-atom's
  convention **and** the `(N_α, N_β)` block structure §3c.0b's sector table
  depends on, so adopting it keeps the T2 backend and the text form aligned by
  construction.
* **Gate set** from ffsim's Table 1, captioned "A universal set of fermionic
  gates": number interaction, number–number interaction, Givens rotation,
  tunneling, orbital rotation. Two scope notes: ffsim's claim is universality
  for circuits conserving particle number **and z-spin**, not all
  number-preserving circuits; and the three entries omitted here
  (number-operator-sum, diagonal Coulomb, quadratic-Hamiltonian evolution) are
  commuting products or special cases of the five, so the subset stays
  universal.
* **Hamiltonian stays out of the circuit file** — `FCIDUMP`, as PySCF and
  ffsim both read. §3e.2's one uncontested finding.

#### Draft grammar

```
FERMIONICQASM 1.0;

mode m[4];              // 4 spinless fermionic modes
mode m[4] spin;         // 4 SPATIAL modes -> 8 wires: 0..3 up, 4..7 down
creg c[4];

load m[0], m[1];        // OCCUPY modes 0 and 1 — see "state preparation" below
num(theta)      m[0];                  // exp(i θ n_0)
numnum(theta)   m[0], m[1];            // exp(i θ n_0 n_1)
givens(theta)   m[0], m[1];            // exp(θ (a†_0 a_1 − a†_1 a_0))
tunnel(theta)   m[0], m[1];            // exp(i θ (a†_0 a_1 + a†_1 a_0))
orbrot($U)      m[0], m[1], m[2], m[3];
measure m[0] -> c[0];
```

#### STATE PREPARATION IS MANDATORY, and the first draft omitted it

**Every gate above is number-conserving.** A file that starts from vacuum can
therefore only ever apply phases to vacuum — nothing can put a particle in the
register, and the language is inert. Worse, the initial occupation **is** the
`(N_α, N_β)` sector that §3c.0b's whole T2 design keys on, so a text form that
cannot express it cannot feed the backend it exists to feed.

`load` is not invented here: qiskit-cold-atom's tutorial has *"we need to
initialize some modes with particles, which is done with a **load**
instruction"*, and ffsim ships `PrepareHartreeFockJW` / `PrepareSlaterDeterminantJW`
as circuit operations.

And the OPTICQASM comparison needs a correction the draft glossed: OPTICQASM
does **not** solve this in the grammar — it dodges it with an out-of-band
default input (`omega-backend-photonics/src/sim.rs:22-24`,
`default_input: Option<slos::FockState>`, defaulting to `|1,1,…,0⟩`). So the
bosonic precedent here is a **side channel**, not a statement, and copying it
would reproduce a gap rather than a design.

#### Delta against `opticqasm.pest` — CORRECTED, and it is not small

| OPTICQASM | FermionicQASM |
|---|---|
| `header = { "OPTICQASM" ~ version ~ ";" }` | `"FERMIONICQASM"` — token |
| `photon_decl = { "photon" ~ ident ~ "[" ~ integer ~ "]" ~ pol_marker? ~ ";" }` | `mode_decl`, `spin_marker?` — one-line analogue |
| `pol_marker = { "pol" }` | `spin_marker = { "spin" }` — same *optionality*, **different wire map** (see below) |
| `gate_app`, `param_list`, `mode_list` | reusable as-is |
| `symbol = @{ "$" ~ (ASCII_ALPHANUMERIC \| "_")+ }` | reusable as-is (the draft misquoted this as `"$" ~ ident`; the real rule admits `$1`) |
| **`creg` — DOES NOT EXIST** | must be invented |
| **`measure … -> …` — DOES NOT EXIST** | must be invented, with a classical-bit reference |
| **`load` — DOES NOT EXIST** | must be invented |

`grep -c "creg\|measure" opticqasm.pest` returns **0**: OPTICQASM's
`statement` is `{ photon_decl | gate_app }` and nothing else. The draft's claim
that the delta was "small" and those rules "unchanged" was true of the rules it
named and false of the example it printed — **three whole statement forms were
missing from the table while appearing in the sample file above it.**

There is a live hazard in that gap: under literally-unchanged rules,
`creg c[4];` does not fail — it **silently parses as a `gate_app` named
`creg`**, while `measure m[0] -> c[0];` is a hard parse error. One of those is
much worse than the other.

**`spin` is NOT a mirror of `pol`.** Both are optional markers, but `pol` maps
wires **interleaved** — `(s,p) → 2s + p` (`opticqasm.pest:14-15`) — while
`spin` maps them in **blocks**, first `N` up then `N` down. Both are defensible;
the point is that the lowering code **cannot be shared**, which "mirroring"
language hides.

`mode` rather than `qreg` is deliberate, exactly as OPTICQASM says `photon`:
it should be a *parse* error to hand a fermionic file to the qubit lane.

#### Two decisions worth arguing with

**1. No mapping in the text.** No `jw`/`bk` keyword, nothing qubit-shaped. The
mapping is a **lowering pass** selected at run time, which is the whole point
of §3e.2's correction — baking JW into the file destroys the choice and makes
the fermionic-native T2 backend unfeedable.

**2. `orbrot($U)` takes a symbol, not a literal matrix.** This is the weak
point and it should be stated rather than discovered: **a text assembly
language is a poor container for an `N × N` complex unitary.** Three options,
and the choice is not obvious:

* *symbol reference* (drafted) — `$U` resolved from a side-channel, reusing
  OPTICQASM's existing `symbol = @{ "$" ~ … }` rule. Keeps the file readable;
  makes it non-self-contained.
* *decompose to `givens` at emission* — self-contained, but destroys gate
  identity, which is exactly the §3e.3 failure that makes a downstream
  comparison measure nothing.
* *inline literal* — self-contained and honest, and unreadable at `N = 52`.

Drafted as the first; **not settled.**

#### Status

**Specification drafted, nothing implemented.** Before any of it is written:
the mode/spin convention should be checked against `qiskit-cold-atom` and
`ffsim` source rather than against the tutorial prose quoted above — the same
VERIFY-BEFORE-IMPLEMENTING rule §3e.1a carries for DITQASM, and for the same
reason.

### 3e.3 The one thing both need from us

Both tracks converge on a single missing capability: **the export path must
preserve gate identity, not just gate semantics.** `RBS` lowered to an
equivalent CX sandwich is semantically correct and destroys the fermionic
structure; a qudit gate lowered to qubit gates is correct and destroys the
qudit structure. In both cases the downstream tool then silently runs a
general-purpose simulator and the comparison measures nothing.

`every_emitted_gate_is_readable.rs` already classifies gates by what QASM 2 can
spell (`RBS => Spec::NotQasm2`). That test is the right place to grow a
**structure-preservation** clause: a gate that must survive export as *itself*
should be marked so, and lowering it should be a refusal rather than a silent
decomposition — the same posture as §3b.2's certificate gate and §3c.0's
`--max-weight`-on-fermions rule.

## 3f. Audits — a taxonomy built from this campaign's own defects

Every class below has a **receipt** from work in this repo in the last week. It
is not a generic checklist; it is the list of ways this codebase has actually
been wrong, which is a different and much shorter list.

The organising lesson: **a prose lesson does not travel.**
`omega-backend-mps/src/sim.rs:528` states the "computed but consulted by
nothing" defect in plain words, correctly, as a lesson — and the identical
defect sat one directory away in `omega-backend-pauliprop` until 2026-08-28.
So every audit below is specified with a **mechanical form** wherever one
exists, and prose only where none does.

### A1 — Computed but never consulted

**Receipt:** `dropped_mass` was accumulated, plumbed to the `Backend` result,
documented as "the CERTIFIED error bound", printed by the CLI, and read by
nothing. Verbatim the defect `sim.rs:528` records fixing in MPS.

**Audit:** for every certificate, budget, bound, fidelity or health metric the
codebase computes — is there a consumer that can *change the outcome*? Printing
is not consuming.

**Mechanical form:** enumerate `pub` struct fields whose names match
`/(mass|weight|fidelity|error|bound|budget|discarded|dropped)/` and find each
one's read sites. A field read only by `Display`/serialisation is a finding.

### A2 — An assertion true of the thing it was written to exclude

**Receipt:** `truncation_turns_the_refusal_into_a_bounded_answer`, doc reading
*"NOT A SILENT FALLBACK"*, asserted only `v.is_finite()` on a configuration
producing `final_terms = 0` and returning `0.0`. Also: three assertions
checking `|err| ≤ dropped_mass` on a bound that cannot be violated.

**Audit:** for every assertion, can it fail? A check that cannot go red is
indistinguishable from one that passes.

**Mechanical form:** **fault injection, systematised.** This campaign did it by
hand 9 times and it caught 9 defects — and once *confirmed a wrong conclusion*
(the `ZERO_C` episode), so it is necessary and not sufficient. Candidate:
`cargo-mutants` over the backend crates, gated to a per-crate budget. Any
surviving mutant in a truncation/certificate path is a finding.

### A3 — The correct thing exists elsewhere and did not travel

**Receipt, four times:** `dropped_mass` present in the crate whose bug report
said it was missing; `apply_quad_perm.cu` carrying the right signed-zero
contract while the CPU kernels did not; `PLAN-SV-PERF.md` §S1b prescribing the
exact test before the work started; `sim.rs:528` stating the lesson as a lesson.

**Audit:** before implementing anything described as missing, grep the tree for
it. This is now standing practice (§5) and it has paid four times.

**Mechanical form:** none general. But a **pre-implementation grep is a
checklist item with a 4/4 hit rate**, which is enough.

### A4 — A retracted claim surviving on other surfaces

**Receipt:** `4c97550` retracted the permutation-exemption claim in kernels,
comments and tests, and left it standing in four other files including
`GATE-EXACTNESS.md` — the project's exactness ledger, which was then *less
accurate than the `.cu` it documents*.

**Audit:** a retraction requires a grep for the retracted words across every
surface, not only the file being edited.

**Mechanical form:** a CI grep for a small list of retired phrases. Cheap, and
the retraction bullet quoting itself (§`bit-identical by construction`) is the
pattern that makes the grep hit intentional rather than a miss.

### A5 — Live constants nobody derived

**Receipt:** two vacuity thresholds, `budget < 2.0` and `dropped_mass < range`,
a factor of two apart, both defensible, neither derived. They **disagreed**,
which is the only reason it was noticed. Had they matched, a coincidence would
have shipped as a rule.

**Audit:** every numeric threshold that gates a result needs a derivation or a
measurement next to it. `DEFAULT_MAX_DISCARDED_WEIGHT = 1e-6`,
`DEFAULT_MAX_TERMS = 1 << 21`, `PAR_MIN_DIM`, the SVD cutoffs, `1e-9`/`1e-12`
tolerances — which of these are derived, which measured, which inherited?

**Mechanical form:** enumerate `const` items with numeric literals in gating
positions; require a doc comment. Weak, but it surfaces the list.

### A6 — A knob that survives syntactically and dies semantically

**Receipt (prospective):** `--max-weight` on a fermionic circuit after
Jordan–Wigner. Pauli weight stops meaning anything, the flag keeps accepting
values and keeps producing numbers. Same shape as A1 one level up: mechanism

**Audit:** for every flag, is there a regime where it still parses and no longer
means what its help text says? Those must refuse, not degrade.

### A7 — Bit-identity asserted on something that is not bit-reproducible

**Receipt, three times in one session**, most recently `raised.to_bits() ==
baseline.to_bits()` on a pauliprop expectation — flaky at 1 ULP because
`PauliSum::terms` is a `HashMap` with a per-process random seed, so summation
order varies per run.

**Audit:** every `to_bits()` / bit-identity assertion must name the property
that makes bit-identity hold. The peer's diagnosis is the useful one:
`to_bits()` gets reached for **when the author wants strength, not when the
property holds**.

**Mechanical form:** grep `to_bits()` in tests; each occurrence needs a
justifying comment. Small, finite, checkable.

### A8 — Skips that read as passes

**Receipt:** a green `ci.sh` run with **8 stages not run**, two of them
MANDATORY on a host that could run them. The script's own closing line —
*"A green run is only as strong as what actually ran"* — is the mitigation, and
it works only because the count is in the banner.

**Audit:** every conditional stage must report its skip in the final summary,
with the count in the line a reader greps. Extend to: *why* it skipped, and

### A9 — Verification scope narrower than change scope

**Receipt:** `cargo test -p <the crate I edited>` came back green twice while
full CI exited **101** — once on `omega-cli` integration tests, once on the
Metal parity crate. Both were downstream of a change in a *different* crate.

**Audit:** a change to a crate requires testing its **reverse dependencies**,
not itself.

**Mechanical form:** `cargo tree -i <crate> --workspace --depth 1` → test that
set — **but it has a hole, found by using it.** Dependents that take the crate
as an **optional** dependency are invisible without the feature enabled. Run on
`omega-backend-mps-cuda` it returns *nothing at all*, while
`grep -rln omega-backend-mps-cuda --include=Cargo.toml crates/` finds five:
`aria-runtime`, `omega-cli`, `omega-server`, `omega-backend-pauliprop-cuda`,
and the crate itself. So for a feature-gated crate the grep is the complete
check and `cargo tree` is the incomplete one — the reverse of the usual advice,
and worth knowing before trusting an empty result as "nothing depends on this".

**Verified, and the first version of this line was wrong**: it said
`cargo tree --invert -p <crate>`, which returns only the crate itself, because
in a workspace `-i` needs `--workspace` to look outside the current member and
`-p` means a subtree filter instead. Written confidently, silently useless —
an A5 in the audit section about A5, caught only by running it.

Run correctly on `omega-backend-pauliprop` it lists **omega-cli** and
**omega-backend-pauliprop-metal** — precisely the two crates whose failures
took two full CI cycles to find — plus `omega-backend-pauliprop-cuda`,
`aria-runtime`, `aria-qec`, `aria-app-spectra`, `omega-server`, `omega-xcheck`
and `omega-bridges`, none of which were tested either. (The first version of
this list omitted `-cuda`: an enumeration narrower than its own output, inside
the audit item about verification scope being narrower than change scope.)

## 3g. Majorana quantum circuits — the text form is Stim, not QASM

### 3g.0 Disambiguation, because this repo now uses "Majorana" for three things

Three unrelated meanings, and confusing them would be expensive:

1. **Majorana operators** `m_k` — the algebra (§3c.2). A basis, nothing more.
2. **Majorana Propagation** (§3c.1–3c.6) — a *classical simulation algorithm*
   for fermionic circuits. Runs on ordinary hardware.
3. **Majorana computing** — *topological quantum computing* with Majorana zero
   modes: a hardware model. This section.

They share the algebra of (1) and nothing else. §3c is about simulating
fermions on a classical computer; §3g is about representing circuits for a
machine whose qubits are MZMs.

### 3g.1 The load-bearing fact: the native instruction is a MEASUREMENT

Majorana-based topological qubits do not have a gate as their primitive. From
the literature, in its own words: *"multi-qubit Pauli measurements are the
native instruction set"*, and *"multi-qubit Pauli measurements rather than CNOT
gates are the native operations"*. Measurement-only topological quantum
computation implements the Clifford group through **projective measurements of
the joint fermionic parity of pairs of MZMs**, plus ancillary MZMs — there is
no braiding step in the modern architectures, the braid is *effected* by a
measurement sequence.

Two consequences that decide the representation:

* A Majorana circuit is a **sequence of joint-parity measurements**, and the
  classical outcomes feed forward. A gate-list format is the wrong shape.
* **Braiding is Clifford-only.** Universality needs magic states. So a Majorana
  logical circuit is *Clifford + magic state injection* — the regime the
  stabiliser formalism handles in polynomial time.

  **RETRACTED: "exactly what `aria-qec` already implements 15-to-1 distillation
  for".** `logical/distill.rs` is an **analytic rate model**, not a protocol:
  `step()` is literally `p ↦ a·p³` (`distill.rs:73-76`) with closed-form
  `acceptance()` and `raw_states_per_output()`. No circuit, no stabiliser
  state, nothing is ever distilled. Its own module doc says so —
  *"This is the analytic resource model… Distilling the actual 15-qubit circuit
  on a backend is a later option"* (`distill.rs:21`) — and I did not read it.
  The eighth A3, and the second time in two reviews that the file's own header
  contained the correction.

### 3g.2 The format: Stim's `MPP`, and the repo already speaks Stim

**OpenQASM 2 and 3 have no multi-qubit Pauli-product measurement.** Neither can
express `measure the joint parity of X₀Y₁Z₂` as a primitive. Adding one would
be inventing a dialect — precisely what §3e argues against.

**Stim has it natively**: `MPP X0*Y1*Z2`. Stim is the de-facto standard for
stabiliser and QEC circuits, and `MPP` *is* the Majorana native instruction
written down.

And this repo **already emits Stim**. `crates/omega-bridges/python/qasm2_stim.py`
is a QASM2 → extended-Stim converter feeding the tsim and ppvm runners, and it
already solves the same shape of problem — vanilla Stim plus documented bracket
tags for what Stim cannot express (`S[T] <q>`, `I[R_X(theta=…)] <q>`). So there
is both a Stim emission path and a **precedent for extending the dialect
carefully rather than inventing one**.

What is missing: **`MPP` appears nowhere in our own code** — not emitted, not
consumed, not in any backend. That is the gap, and it is a specific one.

### 3g.3 What a Majorana lane would actually need

* **`MPP` emission** in `qasm2_stim.py`'s converter and an IR operation for it.
  `GateOp` has `qubits` and a single `classical_bit`; a Pauli-product
  measurement needs a *Pauli string* plus an outcome bit, which the current
  shape does not express. Same structural gap as DITQASM's level-controls
  (§3e.1a) — the IR assumes gates, and these are not gates.
* **A stabiliser backend that supports `MPP`. Question answered by review, and
  in the cheap direction:** `omega-backend-pauli/src/stabilizer.rs` currently
  measures only in the **single-qubit Z basis** (`measure(q)` at `:199`,
  `measure_prob` at `:306`) — no Pauli-product measurement. But the
  `PauliRow::anticommutes` machinery a general `MPP` needs already exists, so
  this is **a feature, not a rewrite**.
* **The Majorana-indexed layer**, which is where §3c pays off twice: a physical
  parity measurement is of `iγ_aγ_b` or a 4-MZM product, i.e. a **Majorana
  monomial** — the same `2N`-bit vector, commutation rule and Hermiticity
  phase specified in §3c.2. One data structure serves both sections.
* **The error model, which is the actually interesting part.** Topological
  protection is against *local* noise and **not** against quasiparticle
  poisoning, which flips fermion parity and is the dominant failure mode. A
  Majorana lane whose noise model is depolarising has modelled the one thing
  the hardware is already good at and skipped the thing it is not.

### 3g.4 Honest scoping

This is **not** a simulator-algorithm problem. Clifford + magic states is cheap
and the repo has stabiliser simulation, magic-state distillation, and a
PyMatching-cross-checked decoder. The work is in the **representation** (`MPP`
in the IR and on the wire) and in the **noise model** (parity poisoning).

**Not claimed:** that anyone needs this. Majorana hardware is at eight physical
qubits and the field, in the same sources, still lacks *"decisive proof of
non-Abelian behavior"* along with scalable materials, parity stability and
single-shot parity readout. This is worth planning because the representation
gap is real and cheap to close, not because there is a machine waiting.

**Reference implementations — gap now CLOSED (see §3h).** The first draft said
§3g named neither an oracle nor an algorithm reference. Both exist:

* **Result oracle: Stim** (Apache-2.0, ★816). `MPP` *is* the Majorana native
  instruction, and Stim is the mature de-facto standard for stabiliser circuits.
* **Algorithm reference: the Microsoft QDK resource estimator** (MIT, ★994),
  whose `qubit_maj_ns_e4` / `qubit_maj_ns_e6` parameter sets define a Majorana
  instruction set **in terms of single- and two-qubit measurements and T
  gates** — independent confirmation, from the vendor's own open tooling, of
  §3g.1's claim that the native instruction is a measurement. Based on
  `arXiv:1610.05289`.

Microsoft's measurement-only surface-code *architecture* remains in patents
rather than open code; that part of the original caveat stands.

> **Stim cannot simulate T gates, and a Majorana machine needs them.** §3g.1
> says braiding is Clifford-only so universality requires magic-state
> injection, and the QDK instruction set cited in the *next* table includes
> `t_gate_*` parameters. This repo already knows Stim's limit: `qasm2_stim.py`
> maps `t → S[T]`, a **bracket-tag extension**, precisely because vanilla Stim
> rejects it, and routes such circuits to tsim/ppvm instead. So Stim is the
> oracle for the **measurement/Clifford fragment**; a T-injected Majorana
> circuit needs tsim or an equivalent. The first draft of this row omitted that
> and would have had someone check a magic-state protocol against a simulator
> that cannot run one.

### 3h.4 Circuit representation — the standards question, answered per track

| track | standard | status | position |
|---|---|---|---|
| qubit | **OpenQASM 2 / 3** | ratified; **in-tree already** (pest grammar, exporter, conformance suite) | keep |
| **fermionic** | **none exists → `FermionicQASM` 1.0, drafted §3e.2a** | searched: no fermionic dialect in OpenQASM 2/3, cQASM or Jaqal; qiskit-cold-atom's `.qasm()` is a deprecated generic method | **IR: yes**, mirroring `CircuitType::Photonic`. **Text form: invent**, mirroring `OPTICQASM` (itself in-house), adopting qiskit-cold-atom's mode/spin conventions and ffsim's gate set. `FCIDUMP` for the Hamiltonian |
| **qudit** | **DITQASM** | de-facto (MQT); **OpenQASM 3 has NO qudit support** | **adopt.** It extends the **OpenQASM 2.0 grammar** — the one this repo already parses |
| **Majorana** | **Stim**, specifically `MPP` | de-facto for stabiliser/QEC | **adopt.** OpenQASM 2/3 have no multi-qubit Pauli-product measurement; Stim does, and `qasm2_stim.py` already emits Stim with a documented dialect-extension pattern |

**The one capability all three new tracks need** (§3e.3): export must preserve
gate **identity**, not just semantics. `RBS` lowered to an equivalent CX
sandwich is correct and destroys the fermionic structure; the downstream tool
then silently runs a general-purpose simulator and the comparison measures
nothing. `every_emitted_gate_is_readable.rs` is where that clause belongs.

## 5. Standing practice

**Parity with Perceval and Piquasso is the guide.** Both are independent
implementations, which is the property that matters: two of our own backends
agreeing may only mean they share a convention, and this project has already
shipped a defect that every internal agreement gate missed. Current state — all
green, nothing weird: Perceval 2/2 (`perceval 1.2.4` + `perceval_interop`),
Piquasso 11/11 (base 4, multimode 4, loss 1, opticqasm-CV 2).

Build the venvs before trusting a green run. An absent venv makes these arms
**skip**, and a skip reads as a pass unless something says otherwise — which is
what `SKIPPED_STAGES` and ci.sh's closing "A green run is only as strong as what
actually ran" exist for.
